# LIGHT LAB

Python bpy 장면과 React + FastAPI 로컬 비교 앱으로 구성한 조명 실험입니다. 배포 패키징은 아직 포함하지 않습니다.

## 로컬 비교 앱 — 최신 실행 방법

조명 5개의 색상·밝기·켜기/끄기, FHD/샘플 선택, Eevee·Cycles 비교와 작업 기록을 갖춘 로컬 화면을 구현했습니다. 사용법과 검증 한계는 [APP.md](APP.md)에 정리했습니다. 일반 macOS 터미널에서 `./start_app.sh`를 실행한 뒤 `http://127.0.0.1:8765`에 접속하세요. 라이트맵 없는 간접광 근사 방식을 사용하며, 이전 프리셋 캐시와 실험 파일은 보존합니다.

아래는 이전 단계의 개발 기록입니다. 현재 앱은 다섯 조명을 각각 독립적으로 조절하며, 실행법은 위의 APP.md를 기준으로 합니다.

## 2단계 — 프리셋·사전 계산 캐시

React/FastAPI 화면은 이번 범위에 포함하지 않았습니다.

아래 버전별 기록은 1단계 장면 개발 이력입니다. 이전의 `run.sh`도 수동 렌더용으로 남겼으며, 현재는 기존 결과를 보존하도록 `renders-manual/`에 저장합니다.

## v13 — 평천장·동일 광택 석재 (렌더 검증 대기)

파형 천장과 파형 때문에 추가했던 벽 상부 마감을 제거했습니다. 천장은 기존 높이 4m의 평평한 20cm 슬래브로 복원하고, 벽·바닥과 동일한 광택 석재 재질을 공유합니다. Roughness 0.16, IOR 1.5, Coat Weight 0.25, Coat Roughness 0.10입니다. 코브의 차광 턱은 기존 무광 재질을 유지합니다.

중앙 패널, 조명, 카메라, Eevee Raytracing OFF, 반사용 Sphere Probe, 라이트맵 CPU 노이즈 제거는 유지합니다. 형상이 바뀌어 라이트맵은 새로 베이크해야 합니다:

```bash
./run.sh
```

결과는 `renders-v13/`에 저장됩니다. 기존 렌더와 v12 소스는 보존했습니다. Python/Bash 구문과 파형·상부 마감 제거를 확인했으며 Blender 실행·렌더 결과는 아직 검증하지 않았습니다.

## v12 — 파형 천장·광택 석재 (렌더 검증 대기)

천장을 실제 곡면 슬래브로 변경했습니다. 아래쪽 표면은 높이 4m를 기준으로 진폭 22cm, 파장 3m의 사인파가 좌우로 이어집니다. 슬래브 두께는 18cm이며 곡면 법선을 부드럽게 처리합니다. 천장이 올라간 곳의 벽 틈은 상부 마감으로 닫습니다. 천장과 코브 차광 턱은 무광 흰색 재질입니다.

벽·바닥은 금속이 아닌 밝은 광택 석재로 변경했습니다. 대리석과 비슷한 반사감을 목표로 Roughness 0.16, IOR 1.5, Coat Weight 0.25, Coat Roughness 0.10을 적용했습니다. 무늬 대신 표면 반사감 위주로 변경했으며 기존 콘크리트 범프는 제거했습니다. 중앙 패널·조명 위치·광량·카메라는 유지합니다.

Eevee Raytracing/Fast GI는 계속 OFF입니다. 반사용 Sphere Light Probe와 방 형태의 Box Parallax를 추가해 환경 반사를 근사합니다. 이 프로브는 간접광 볼륨이 아니며, 광택 표면에서 보이는 반사용입니다. 정밀한 평면 거울 반사나 여러 번 반사되는 장면을 보장하지 않습니다. Cycles는 원래 물리 재질과 광원으로 반사를 계산합니다. 반사 프로브 준비 비용은 Eevee 렌더 호출 시간에 포함됩니다.

구조와 재질이 바뀌어 기존 라이트맵은 재사용하지 않습니다. 이번에는 다음 명령으로 새로 베이크해야 합니다:

```bash
./run.sh
```

결과는 `renders-v12/`에 저장됩니다. 이전 장면을 처리하는 `refine_lightmaps.sh`는 이번 변경에 사용하지 않습니다. 벽·바닥과 무광 천장에 각기 원래 재질을 유지한 채 라이트맵을 생성하도록 베이크 대상을 확장했습니다. CPU 노이즈 제거, 원시 맵 보존, 엔진별 출력 분리를 유지합니다.

검증한 사항: Python/Bash 구문, 파형 메시가 닫힌 구조인지, 표면 법선 방향, 높이 범위, 베이크 오류 복구 경로. Blender 실행·실제 베이크·반사 강도·시각 품질은 아직 검증하지 않았습니다. 높이 범위는 실내 천장 표면 3.78~4.22m, 슬래브 외부 최고 4.40m입니다.

참고: [Blender Sphere Light Probe](https://docs.blender.org/UATEST/manual/en/4.5/render/eevee/light_probes/sphere.html)

## v11 — 라이트맵 CPU 노이즈 제거 (맵 처리 완료, 최종 렌더 대기)

v10은 자연스러운 밝기를 얻었지만 128 samples로 베이크한 텍스처의 노이즈가 최종 이미지에 남았습니다. Eevee 최종 샘플은 이미 512라서 텍스처 속 노이즈를 추가 누적으로 제거할 수 없습니다. 기존 EXR에서 표면 입자를 직접 확인했습니다.

Blender에 포함된 OpenImageDenoise를 **CPU 장치로 명시적으로 선택**해 HDR 라이트맵 26장을 처리했습니다. 처리 시간은 2.056초이며 EXR 입출력을 포함합니다. 모든 출력의 유한 픽셀값과 파일 수를 확인했고, 같은 톤 매핑으로 원본/처리된 바닥 UV 맵을 시각 비교해 입자가 줄어든 것을 확인했습니다. 최종 Eevee 이미지의 개선 여부는 아직 확인하지 않았습니다. 이 작업은 bpy나 Blender 앱을 시작하지 않았습니다.

기존 v10 베이크를 재사용하여 새 맵으로 렌더링하려면 다음을 실행합니다:

```bash
./refine_lightmaps.sh
```

결과는 `renders-v11/`입니다. `lightmaps/`의 26개 EXR은 이미 준비됐으므로 재베이크를 하지 않습니다. 스크립트는 성공한 `renders-v10/light_lab.blend`를 열고 라이트맵 이미지 노드만 교체하여 Eevee와 Cycles를 렌더링합니다. 기존 v10 데이터는 유지합니다. 원본 장면의 카메라·광량·재질의 물리적 속성은 바꾸지 않습니다. 엔진별 출력 분리도 유지해 Cycles는 이 라이트맵을 사용하지 않습니다.

노이즈 제거는 선형 HDR RGB 텍스처에만 적용하며, 최종 Eevee 프레임에 흐림 처리를 하지 않습니다. OIDN은 광선을 추적하는 기능이 아닙니다. 최종 Eevee는 Raytracing/Fast GI OFF, 512 samples를 유지합니다. color-only 노이즈 제거이므로 UV 경계나 작은 밝기 디테일이 과도하게 부드러워지는지 새 렌더에서 확인해야 합니다.

`renders-v11/lightmaps/denoise_report.json`에 맵별 처리 시간과 평균값을 기록합니다. 새 `render_report.json`의 렌더 시간에는 원래 v10 베이크와 CPU 맵 준비 시간이 포함되지 않으며 각각의 비용을 별도로 봐야 합니다.

새 장면/색상으로 처음부터 베이크할 때 사용하는 `./run.sh`도 맵 노이즈 제거를 포함하도록 수정했습니다. 새 베이크 기본값은 256 samples이며, 결과는 혼동을 피하기 위해 `renders-v11-fresh/`에 저장합니다. 원시 맵은 `lightmaps/raw/`, 처리된 맵은 `lightmaps/`에 따로 저장합니다. 새 베이크 보고서의 전체 시간에는 노이즈 제거도 포함됩니다. 이 전체 실행 경로는 아직 Blender 런타임에서 검증하지 않았습니다.

검증: CPU OIDN 실제 실행·EXR 검증·바닥 맵 시각 비교·Python/Bash 구문 검사·오류 복구 검사 통과. Blender 렌더링은 실행하지 않았습니다.

참고: [Open Image Denoise 공식 API](https://github.com/RenderKit/oidn/blob/master/doc/api.md)

## v10 — 래스터화 + 표면 라이트맵 (렌더 검증 대기)

v8의 공간·카메라·광원을 기준으로 Eevee 렌더 중 Raytracing과 Fast GI를 끄고 최종 렌더 샘플을 512로 고정했습니다. 간접광 볼륨 프로브는 생성하지 않습니다. 대신 콘크리트 벽·바닥·천장·차광 턱에 겹치지 않는 UV와 개별 라이트맵을 생성합니다. 기존 베벨을 메시에 적용하고 두 엔진에 같은 형상을 사용합니다. 재질 범프는 v8과 같이 0입니다.

일반 macOS 터미널에서 실행합니다:

```bash
./run.sh
```

결과: `renders-v10/eevee.png`, `cycles.png`, `light_lab.blend`, `render_report.json`, `render.log`, `lightmaps/*.exr`, `lightmaps/bake_report.json`. 원래 이미지·스크립트는 이전 버전 폴더에 보존합니다. 라이트맵은 EXR로 저장하고 `.blend` 안에도 포함합니다. 저장된 장면에서 엔진을 전환해도 Eevee/Cycles용 Material Output이 각각 선택됩니다.

### 빛의 구성과 비교 조건

라이트맵은 Cycles가 미리 계산합니다. 최종 Eevee 렌더는 레이트레이싱 없이 이 맵과 일반 광원의 직접광을 사용합니다. 따라서 비교 명칭은 **래스터화 + 사전 계산 조명 대 패스트레이싱**입니다. 모든 과정에서 광선 추적을 배제한 실험이 아닙니다.

간접광 베이크는 `DIFFUSE / INDIRECT + COLOR`이며 색상이 포함된 선형 확산 반사광을 저장합니다. Eevee는 발광 메시의 직접 조명을 자동으로 계산하지 않으므로, 일반 광원 에너지를 잠시 0으로 만든 별도 `DIFFUSE / DIRECT + COLOR` 베이크로 패널·발광 스트립의 직접 기여만 저장합니다. 에너지는 두 엔진 렌더 전에 복구합니다. 일반 광원의 직접광은 Eevee가 계산하므로 이중 합산하지 않습니다. Cycles 재질 출력에는 라이트맵을 연결하지 않아 라이트맵이 다시 발광하는 중복 계산을 피합니다. Eevee에 프로브도 추가하지 않습니다. 광원 위치·색·세기는 바꾸지 않았습니다.

이 방법은 정적인 무광 표면을 위한 근사입니다. 동적인 반사·금속·조형물 이동의 정확성을 보장하지 않습니다. 조명 색상·위치나 공간 형상을 바꾸면 맵을 다시 구워야 합니다. 현재는 실행할 때마다 새로 베이크합니다.

### 품질과 시간

초기 실험 설정은 큰 표면 512px, 작은 부재 128px, 베이크 128 samples입니다. UV 여백과 2px bake margin을 사용합니다. 노이즈 제거가 베이크에 적용됐다고 가정하지 않으며, 빛샘·UV 경계·남은 노이즈는 실제 이미지에서 검증해야 합니다. 필요 시 다음처럼 높일 수 있습니다:

```bash
./run.sh --lightmap-resolution 1024 --lightmap-samples 256
```

`lightmap_bake.seconds`는 UV/형상 준비, 두 패스 베이크, EXR 저장·패킹을 포함합니다. 각 패스 시간은 `passes`에 따로 기록합니다. `renders[].seconds`는 기존과 같이 최종 렌더 호출 시간입니다. `eevee_bake_plus_render_seconds`는 베이크 준비와 Eevee 렌더 합계이며 Blender 시작과 최초 장면 생성 시간은 제외합니다. 변경 후 첫 결과 비교에는 베이크 비용을 포함해야 합니다.

베이크 오류·비정상 픽셀·모든 간접광 맵이 검정인 경우 성공으로 처리하지 않고 중단합니다. 상세 기록은 `lightmaps/bake_report.json`과 `render.log`를 확인합니다. 매번 결과 폴더의 파일은 덮어씁니다.

### 현재 검증 상태

Python/Bash 구문 검사, 프로브/실시간 RT 비활성 설정, 엔진별 출력 분리와 오류 시 설정 복구·실패 보고 경로를 점검했습니다. 이 채팅에서 Blender를 실행하지 않았으므로 베이크 API 실행 성공과 실제 얼룩 개선 여부는 아직 검증되지 않았습니다.

참고: [Blender Cycles Render Baking](https://docs.blender.org/UATEST/manual/en/4.5/render/cycles/baking.html)

## 비교 진단 결과와 v9 (새 경로 렌더 검증 대기)

`diagnostics-v8/`의 네 이미지와 JSON을 확인했습니다. 512 최종 렌더 샘플에서 잔노이즈가 줄었지만, 벽·바닥 접합부의 어두운 띠는 남습니다. 광원의 그림자를 꺼도 큰 차이가 없고, 프로브를 숨기면 실내 대부분이 검게 됩니다. 그림자 끄기 실험은 기존 베이크 데이터 속의 그림자까지 제거한 것은 아닙니다. 따라서 직접광 그림자만의 문제가 아니며, 간접광 경로에 남은 차이는 추가 확인이 필요합니다. 베이크/보간 중 어느 단계의 문제인지는 이 비교만으로 확정하지 않습니다.

v8은 Raytracing이 꺼져 있었습니다. v9는 확인된 노이즈 개선을 위해 최종 렌더 샘플 512를 적용하고, 남은 간접광 차이를 비교할 새 경로로 Eevee Screen Raytracing을 활성화합니다. 전 해상도, 거친 표면까지 추적, Spatial/Temporal/Bilateral 노이즈 제거를 설정하고 Fast GI는 끕니다. 화면 밖 정보는 여전히 프로브에 의존하므로 이 변경이 어두운 띠를 없앤다고 보장하지 않습니다. 새 광원이나 World 광량은 추가하지 않았습니다.

```bash
./run.sh
```

새 결과는 `renders-v9/`에 저장됩니다. v9 자체의 실행·이미지 검증은 아직 수행하지 않았습니다. 베이크 샘플 2048과 최종 렌더 샘플 512는 다른 설정이며, 각각 별도 시간과 함께 JSON에 기록합니다. 스크린 레이트레이싱은 Cycles 패스트레이싱과 동일한 방식이 아닙니다.

선택적으로 같은 512 샘플에서 새 추적 경로의 영향만 비교할 수 있습니다:

```bash
./run.sh --no-raytracing --output renders-v9-probe-only
```

기존의 512 샘플 진단 결과는 `diagnostics-v8/02_samples_512.png`에서 바로 확인할 수 있습니다. 설치된 Blender 4.5의 UI와 공식 Default Raytracing 프리셋에서 설정명을 확인했고 Python/Bash 구문 검사를 통과했습니다. Blender는 이 채팅에서 실행하지 않았습니다.

## v8에서 개선 없음 — 비교 진단 준비

실제 v8 JSON에서 범프 0, Normal Bias 0.7, Facing Bias 0 적용을 확인했지만 결과 이미지는 v7과 유사했습니다. 재질이 주원인이라는 추정은 지지되지 않습니다. 제작 장면 설정을 추가로 변경하지 않고, 저장된 v8 장면으로 다음 비교를 수행하는 `diagnose.sh`를 준비했습니다. Blender 실행과 결과 판독은 아직 수행하지 않았습니다.

```bash
./diagnose.sh
```

결과는 `diagnostics-v8/`에 저장됩니다. 01은 기존 설정, 02는 최종 렌더 샘플만 512로 변경, 03은 광원 그림자만 비활성화, 04는 간접광 프로브를 렌더에서 숨깁니다. 03/04는 최종 디자인이 아닌 원인 분리용입니다. 저장된 장면·기존 결과·`run.sh`는 바꾸지 않습니다. 기본 Raytracing/Fast GI 상태도 JSON에 기록합니다. 비교 결과로 샘플 노이즈, 직접광 그림자 계산, 프로브 간접광의 영향을 구분합니다.

## Eevee 표면 법선·간접광 진단 — v8 (렌더 검증 대기)

Cycles 로그의 첫 샘플 시작은 약 32.76초 지점이며 커널 로딩이 상당 부분을 차지합니다. 이 1회 측정으로 반복 렌더 속도를 단정할 수 없습니다. 근거 파일: `renders/render_report.json`, `renders/render.log`, `validation_status.json`.

## 장면

12×10m 갤러리, 밝은 무채색 콘크리트 바닥·벽·천장, 조형물, 발광 패널, 차광 턱 뒤에서 천장을 비추는 코브 광원, 고정 카메라로 구성됩니다. 외부 모델·텍스처·애드온은 필요하지 않습니다. 콘크리트의 미세 표면은 Noise/Bump 노드로 생성합니다.

두 엔진에 같은 카메라·형상·재질·광원을 사용합니다. v2에는 두 코브 광원과 발광 패널만 남겨두며, Eevee의 간접광 프로브 베이크는 포함하지 않았습니다.

## 실행

이 폴더가 현재 프로젝트의 `outputs/light-lab`에 있으면 다운로드한 Blender를 자동으로 찾습니다. 일반 macOS 터미널에서 아래 명령을 실행하세요. 경로를 옮겼다면 `/Applications/Blender.app` 또는 `BLENDER_BIN`을 사용합니다.

```bash
cd '/path/to/light-lab'
./run.sh
```

다른 Blender 설치 경로:

```bash
BLENDER_BIN='/Applications/Blender.app/Contents/MacOS/Blender' ./run.sh
```

색상 변경(선형 RGB, 0~1; 두 엔진 모두에 적용):

```bash
./run.sh --color 1.0 0.25 0.08
```

Cycles CPU로 명시적으로 실행:

```bash
./run.sh --device CPU --engines cycles
```

이 CPU 옵션도 Blender 앱 자체가 시작될 수 있어야 합니다. 아래 bpy 모듈 경로 역시 이 채팅의 제한 실행 환경에서는 실패했습니다. `--device CPU`로 Eevee의 GPU 필요 조건이 없어지는 것은 아닙니다.

직접 실행 예시(Blender 4.5.15 권장):

```bash
'/Applications/Blender.app/Contents/MacOS/Blender' -b --factory-startup --python-exit-code 1 --python scene.py -- --output renders --device METAL
```

`renders-v10/eevee.png`, `renders-v10/cycles.png`, `renders-v10/light_lab.blend`, `renders-v10/render_report.json`, `renders-v10/render.log`가 생성됩니다. 같은 출력 폴더의 결과는 덮어씁니다. `.blend`는 두 엔진 중 마지막으로 실행한 설정으로 저장되며, 장면 자체는 같습니다. Blender에서 열고 Render Engine을 바꿔 재렌더링할 수 있습니다.

## 시간과 품질

480×360 PNG, Cycles 24 samples, denoise 사용, 고정 seed 42, AgX. 각 엔진을 한 번씩 렌더링합니다. `render_report.json`의 `seconds`는 `time.perf_counter()`로 측정한 렌더 호출부터 PNG 저장 완료까지의 실제 시간입니다. 첫 셰이더/커널 준비가 포함되며 Blender 시작·다운로드·장면 생성 시간은 제외됩니다. 한 번의 저해상도 검증으로 일반적인 속도 우열을 결론 내리지 않습니다.

## 이전 제한 실행 환경의 진단 기록

2026-10-29, MacBook Air Apple M2(8 CPU / 8 GPU 코어), 통합 메모리 16GB, macOS 27.0.1 arm64. 기존 Blender 설치를 찾지 못해 공식 4.5.15 LTS arm64를 프로젝트 `work/runtime`에 준비했습니다. 시스템 Applications 폴더는 변경하지 않았습니다.

- OS 하드웨어 조회: Metal Supported.
- 현재 자동 실행 세션의 Metal API `MTLCreateSystemDefaultDevice`: null. 하드웨어 지원과 현재 프로세스의 장치 접근은 구분해야 합니다.
- Blender CLI: 버전 출력은 정상. 최소 장면/최소 Python 실행도 Python 진입 전 Metal 초기화에서 SIGSEGV(종료 코드 139).
- 백트레이스: `supports_barycentric_whitelist → MTLBackend::metal_is_supported`. 이 세션의 장치 조회 실패와 일치하지만 구체적 OS/세션 원인을 확정한 것은 아닙니다.
- DMG 마운트도 DiskManagement 사용 불가로 실패하여, 공식 배포본을 7-Zip으로 직접 추출했습니다.

`environment.json`, `metal_probe.json`, `blender.crash.txt`, `render.log`에 진단 기록이 있습니다. 위 기록은 일반 터미널 실행 이전에 발생한 실패입니다. 이후 일반 터미널에서 두 렌더가 모두 성공하여 1단계 검증을 완료했습니다. 제한 실행 환경에서는 4.2.23과 bpy 4.5.15도 실패했으므로 해당 경로의 반복 실행은 중단합니다.

## 이 프로젝트에서 준비한 bpy 우회 실행

Blender 앱 시작 단계에 의존하지 않고 같은 버전의 bpy 모듈을 직접 불러 CPU 경로를 검증하는 명령입니다. 런타임과 모듈은 사용자 결과물 폴더가 아닌 프로젝트 `work`에 있습니다. **이 세션에서는 이 명령도 초기화 중 SIGSEGV로 실패했습니다.**

```bash
cd '/path/to/light-lab'
PYTHONPATH="$PWD/work/bpy" work/runtime/extracted/Blender/Blender.app/Contents/Resources/4.5/python/bin/python3.11 outputs/light-lab/scene.py -- --output outputs/light-lab/cpu-validation --device CPU --engines cycles
```
